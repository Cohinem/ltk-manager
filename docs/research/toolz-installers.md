# Toolz installation contracts

Research date: 2026-09-14. Product names are **wad toolz** and **tex toolz**. Repository, executable and registry identifiers retain their upstream spelling.

This is source inspection, not a Windows execution test. The inspected main commits are wadtools `461a300877129a0bfb65b03379cbac892f37edf1` and ltk-tex-utils `360da04c4fcdc66670e711289d0b706927114394`. Latest release tags are `v0.5.7` and `v0.3.0`. The relevant installer and registration files have no changes between these releases and the inspected commits. [wad comparison](https://github.com/LeagueToolkit/wadtools/compare/v0.5.7...461a300877129a0bfb65b03379cbac892f37edf1), [tex comparison](https://github.com/LeagueToolkit/ltk-tex-utils/compare/v0.3.0...360da04c4fcdc66670e711289d0b706927114394)

## Installer scripts

| Contract                                                     | wad toolz                                                              | tex toolz                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Script                                                       | `scripts/install-wadtools.ps1`                                         | `scripts/install-windows.ps1`                                             |
| Default directory                                            | `%LOCALAPPDATA%\wadtools\bin`, fallback `%USERPROFILE%\.wadtools\bin`  | `%LOCALAPPDATA%\LeagueToolkit\ltk-tex-utils`                              |
| Options                                                      | `InstallDir`, `Repo`, `ShellIntegration`, `NoShellIntegration`         | `Owner`, `Repo`, `InstallDir`                                             |
| Release selection                                            | GitHub latest release, heuristic asset selection                       | GitHub latest release, named exe and optional named DLL                   |
| Installed filenames                                          | `wadtools.exe`                                                         | `ltk-tex-utils.exe`, `ltk_tex_thumb_handler.dll`, `bin\ltk-tex-utils.cmd` |
| PATH                                                         | Always adds installation directory to user PATH                        | Always adds shim directory to user PATH                                   |
| Explorer registration                                        | Prompt, or explicit yes/no switches. Noninteractive default is enabled | None. Prints shell and handler commands                                   |
| Version pinning, checksum verification, removal, JSON result | None                                                                   | None                                                                      |

Both scripts directly overwrite the exe. The wad shell-registration step is best effort and does not check the native command exit code. The tex DLL copy tries renaming a locked destination to `.old`, then copies the new DLL. A leftover locked `.old` can prevent a subsequent replacement. The retired `install-thumbnail-handler.ps1` prints migration instructions and exits 1. These scripts are human installation entry points, not complete management protocols. [wad installer](https://github.com/LeagueToolkit/wadtools/blob/461a300877129a0bfb65b03379cbac892f37edf1/scripts/install-wadtools.ps1), [tex installer](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/scripts/install-windows.ps1), [retired installer](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/scripts/install-thumbnail-handler.ps1)

## Releases and architecture

The actual wad Windows asset is `wadtools-0.5.7-windows-x64.zip`, accompanied by a `.sha256` asset. The tex Windows assets are `ltk-tex-utils-windows.exe` and `ltk-tex-thumb-handler.dll`. GitHub release API asset records currently contain SHA-256 digests for all three downloads. Exact release resolution must precede downloading so an operation never mixes versions. Both release workflows target Windows `x86_64-pc-windows-msvc`. There is no native Windows ARM64 shell-handler asset. Support should initially be Windows x64, with ARM64 explicitly unsupported rather than assuming an emulated exe implies an Explorer-compatible DLL. [wad release](https://github.com/LeagueToolkit/wadtools/releases/tag/v0.5.7), [tex release](https://github.com/LeagueToolkit/ltk-tex-utils/releases/tag/v0.3.0), [wad release API](https://api.github.com/repos/LeagueToolkit/wadtools/releases/latest), [tex release API](https://api.github.com/repos/LeagueToolkit/ltk-tex-utils/releases/latest), [tex workflow](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/.github/workflows/release-plz.yml)

## Explorer surfaces

### wad toolz

`wadtools shell install`, `uninstall`, and `status` manage classic per-user context menus. Registry paths are `HKCU\Software\Classes\*\shell\wadtools` with a WAD filename filter, and `HKCU\Software\Classes\Directory\shell\wadtools`. They expose extraction and hashtable actions for `.wad` / `.wad.client`, plus extraction on folders. Installation resets the existing tool-owned subtree and embeds the current executable path. Uninstallation removes these fixed subtrees regardless of which executable originally installed them. Status is human text and returns success even when entries are absent or stale. [shell implementation](https://github.com/LeagueToolkit/wadtools/blob/461a300877129a0bfb65b03379cbac892f37edf1/crates/wadtools/src/shell.rs)

### tex toolz context menus

`ltk-tex-utils shell install`, `uninstall`, and `status` are separate from handlers. Classic menus are under `HKCU\Software\Classes\SystemFileAssociations\.{tex,dds,png}\shell\ltktexutils` and `HKCU\Software\Classes\Directory\shell\ltktexutils`. They expose information/decoding for TEX, encoding for DDS/PNG and batch decoding for folders. `shell install --classic` requests the classic menu. Default install attempts a Windows 11 sparse package, requiring the colocated handler DLL and Developer Mode. It falls back to classic on unsupported conditions or modern-registration failure. The modern path invokes Windows `powershell.exe` and `Add-AppxPackage`, with a persistent manifest under `%LOCALAPPDATA%\LeagueToolkit\ltk-tex-utils-shell`. Even `shell install --classic` calls modern package removal before writing classic keys. Uninstall warns and continues when package removal fails. Status has no JSON contract and package probing can hide failures. [shell commands](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-utils/src/shell/mod.rs), [modern package](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-utils/src/shell/modern.rs)

### tex toolz handlers

`handler install`, `handler uninstall`, and `handler status` manage one bundle: TEX thumbnails, preview pane and property/details integration. Independent thumbnail, preview and property switches do not exist. Context menus can be managed separately. Registration uses machine-wide COM/shell registration and an administrator-owned DLL copy at `%ProgramFiles%\LeagueToolkit\ltk-tex-thumb-handler\ltk_tex_thumb_handler.dll`. Never register the machine-wide COM server against a user-writable Manager installation directory. [handler CLI](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-utils/src/handler.rs), [DLL registration](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-thumb-handler/src/registration.rs)

Default installation takes over foreign ProgID thumbnail/preview slots and competing OpenWith entries, saving prior state for uninstall. `handler install --no-override` disables that additional takeover but does not undo an existing override. It is not a comprehensive no-clobber guarantee: base registration still writes extension slots and property-handler registration. Restoration is best effort and does not consistently check whether another application changed the slot after installation. The fixed Program Files location also cannot distinguish a Manager installation from a standalone installation. Safe takeover and removal therefore need explicit ownership checks beyond the existing CLI. [handler ownership](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-utils/src/handler.rs), [backup and restoration](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-thumb-handler/src/registration.rs)

The handler CLI self-elevates only when stdin is a terminal. A hidden child with captured output cannot rely on this path to show UAC. Manager needs an explicit narrow elevated launch or an upstream GUI-compatible elevation contract. Keep the main application unelevated. The existing CLI waits for the elevated process and maps UAC cancellation to failure. Handler updates rename a loaded Program Files DLL to `.dll.old`, and uninstall can leave that locked file behind. Unregistering does not mean every binary has been deleted or every running Explorer process has loaded the new DLL. [elevation and DLL staging](https://github.com/LeagueToolkit/ltk-tex-utils/blob/360da04c4fcdc66670e711289d0b706927114394/crates/ltk-tex-utils/src/handler.rs)

## Recommended Manager contract

The following are design recommendations derived from the constraints above:

- Resolve and verify pinned release assets in the backend, stage into versioned Manager-owned directories, and invoke upstream registration commands with argument arrays. Do not execute scripts from mutable `main` or reproduce their latest-only PATH behavior.
- Treat installation, context menus, handler bundle and cleanup as separate observed states. A successful child exit is insufficient proof of Explorer state.
- Discover standalone installs from the documented directories, PATH and registered target paths. Record them as external. Never execute arbitrary discovered binaries for probing or delete their files automatically.
- Offer explicit takeover of existing Explorer registrations after showing their current owner/path. Maintain a Manager ownership receipt, but recheck live registry/package targets immediately before mutations.
- Gate full management on structured upstream inspection reporting every menu target, package identity/location, handler DLL/version, all registration slots, takeover backups and partial failures. Support conditional removal against expected ownership and truthful native exit codes.
- Keep a single handler-bundle control. Default to preserving foreign handlers, and require an explicit product action before replacement. `--no-override` alone does not prove preservation.
- Preserve the old executable and DLL until new registration is verified. Updates to an enabled machine-wide handler need UAC again. Do not update the displayed handler version merely because the downloaded CLI is newer.
- Do not terminate Explorer automatically. Track restart-needed or pending-cleanup states and retry deletion after locks clear. Use unique retirement paths upstream to support repeated updates before Explorer restarts.
- Remove Explorer registrations before deleting managed files. On UAC cancellation, ownership conflict or incomplete unregister, retain the working files and expose retryable state.

A versioned no-PATH Manager installation is compatible with the CLIs because menus record absolute executable paths. It does not eliminate the machine-wide handler's fixed-path collision with standalone installations. Shipping against the current CLI requires carefully verified registry/package probes and a privileged execution boundary, or upstream contract work first.
